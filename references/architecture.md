# 架构设计与分层选择

用于新应用框架、新业务模块、模块边界重构或分层架构审核。局部修改沿用已选结构；只有本次确实改变模块职责、模块协作方式或依赖方向时才重新判断相关部分。将结论纳入当前 Superpowers 设计/计划，不另建一套流程或文档。

## 从业务和约束推导职责

先用一条主要操作串起输入、规则、状态变化、数据/外部副作用、结果与失败，再提取真正影响模块划分的依据：

| 设计输入 | 需要确定的内容 |
|---|---|
| 业务流程与不变量 | 什么条件下允许操作，哪些规则始终不能被破坏，失败后应保持什么状态 |
| 数据与事务归属 | 谁拥有规则和状态、谁负责写入，哪些变化必须原子完成，哪些外部行为无法回滚 |
| 调用方与真实变化 | 页面、后台任务等如何复用同一业务操作；哪些依赖已有不同实现，差异是什么 |
| 影响设计的约束 | 实际存在的延迟、并发、一致性、权限、可测试性或部署要求，以及已有项目约定 |

只讨论有依据且影响当前选择的约束；未知目标不虚构数值。不阻塞选择的信息注明假设；无法确定关键业务意图时才提问。小项目可用几句话完成这些判断。

## 模块与公开接口

先按业务能力归属组织模块，再决定模块内部是否需要技术分层。按业务组织与按技术分层可以组合；一个业务模块可以先只有几个函数。

为本次涉及的重要模块说明下列内容，可用一小段话或一行表格，不给每个文件强加模板：

| 内容 | 设计要点 |
|---|---|
| 职责与所有权 | 负责哪项业务能力，拥有哪些规则/状态，与相邻模块如何分工 |
| 公开接口 | 调用操作、业务输入输出、前置条件、不变量、错误和必要的调用顺序；配置及性能约束仅列调用者确实需要知道的部分 |
| 内部实现 | 将数据映射、算法步骤、供应商协议等内部细节藏在模块内，避免调用者拼装其内部流程 |
| 副作用与事务 | 是否写库或调用外部服务；谁开启/提交事务，失败、超时和重复调用如何处理 |
| 依赖与变化 | 允许使用哪些公开能力；典型业务规则或外部实现变化应主要落在哪个模块 |

同进程模块通过公开操作协作，调用者不直接改写其他模块内部状态或绕过其规则。必须同库原子完成的跨模块变化，由明确的用例协调同一事务，不因目录分层拆成远程调用。已有独立应用时遵守其通信契约，不能靠导入另一个应用的内部包绕开它。

## 选择最小够用的模式

| 当前实际条件 | 适合的组织与分层方式 |
|---|---|
| 简单读写、少量校验 | 接口、业务函数、数据访问逻辑分责；允许少量文件和具体函数依赖，省去无行为的转发层 |
| 多项业务能力有独立规则和变化原因 | 按业务模块组织单体，模块间用公开操作协作，模块内部按需要分层 |
| 复杂规则、状态转换或跨步骤事务 | 用例负责流程与事务，纯规则模块负责计算和不变量；只拆出实际复杂部分，不强制完整 DDD |
| 外部依赖已有真实多实现，调用方需要统一语义 | 在该处定义由调用方需要决定的端口，具体适配器处理各自协议，装配入口绑定实现；其他模块保持原有结构 |

这些条件可同时成立，模式可以局部组合，不是项目从小到大的固定升级路线。只存在一个外部实现时可先注入具体函数/对象，不为假想供应商或复用创建端口。拆分独立服务还需实际的部署、故障隔离或团队所有权依据，不能由目录数推出。

说明所选方式如何满足业务约束、主要代价，以及增加或省略某层的理由；复用已在 Superpowers 设计阶段完成的方案比较。外部副作用不随本地事务回滚，需明确执行时机、结果状态和恢复责任，具体超时与重放语义见 [HTTP 参考](http.md)。

## 分别描述调用与源码依赖

运行时箭头表示“调用”，源码箭头表示“导入或依赖类型定义”。为本次方案分别用一行箭头或表格说明，不能用一张未标注的调用链代替两者。

| 所选部分 | 运行时调用示例 | 允许的源码依赖 |
|---|---|---|
| 轻量分层 | 接口调用业务函数，业务函数调用数据访问函数 | `api → business → data_access`；简单查询可 `api → data_access`；数据访问不导入路由或用例 |
| 分离纯规则 | 用例取得业务数据后调用规则，再保存结果 | `use_case → rules`；规则只依赖业务值及必要的纯工具，不导入 HTTP、ORM、配置加载或应用入口 |
| 局部端口与适配器 | 用例经端口调用当前绑定的具体适配器 | `use_case → port ← adapter`；装配入口导入用例和适配器，用例不导入具体适配器；端口不依赖供应商 SDK 或数据库驱动 |

只采用与所选方式对应的规则。端口可使用纯业务类型；具体适配器负责把外部格式映射成该接口要求的结果和错误。装配入口负责具体资源的创建与绑定，业务操作接受已准备的依赖。

前端沿用 [前端参考](frontend.md#职责与依赖) 的导入方向与状态归属，业务流程通过相关功能的公开能力或组合层协调，不因后端选择端口模式就给每个前端请求增加一层包装。

所有方式都应避免循环导入。公共能力不反向导入业务模块；不同业务模块只使用约定的公开入口，不深导入对方内部实现。按本次方案列出需要守住的允许/禁止依赖，再映射到现有 lint、架构测试或依赖检查；没有现成工具时说明实际检查方式，不能把“目录已经分开”当作验证。

## 检查设计是否有用

- **接口可理解**：调用者能否通过公开接口理解操作及错误，而不必阅读内部 SQL、协议和步骤？
- **变化可局部处理**：选一个实际可能发生的业务规则或外部实现变化，指出会修改哪些模块及原因；若多个调用方重复同一规则，重新检查归属。
- **分层承载行为**：删除某层后若约束与封装都没有损失、调用反而更清楚，考虑合并；若重要规则会散落到调用方，则该模块确实承担了职责。不按行数评价模块深度。
- **可从接口验证**：通过业务公开操作验证正常结果、不变量、事务失败和权限范围；确需端口的部分验证不同适配器遵守同一契约，内部实现可以替换而无需调用者了解细节。

将业务依据、重要模块接口、选择与代价、两种依赖关系及对应验收方式放进已有设计的相关段落。实施时沿用主入口的文档同步与验证规则；审核时只报告有证据的问题。输出应能解释划分的原因，而不只是给出目录树。
